# План: учёт времени сотрудников в программе

## Идея

Логировать, сколько времени каждый сотрудник реально провёл в CRM. У нас уже
есть presence (см. `backend/app/realtime/presence.py`): WS-соединение
`/ws/events` на каждый коннект делает `presence.connect`, на heartbeat —
`presence.heartbeat` (раз в 30с), на разрыв — `presence.disconnect`; упавшие
воркеры подбирает `sweeper`. Это ровно те три точки жизненного цикла, из
которых складывается «время в программе». Переиспользуем их.

## Ключевое ограничение, которое надо осознать

**Presence эфемерен.** Он живёт только в Redis (SET + ZSET с TTL) и отвечает
на вопрос «кто онлайн **прямо сейчас**». Истории там нет и быть не должно —
ключи протухают. Поэтому для учёта времени presence сам по себе не подходит:
нужна **отдельная персистентная таблица интервалов** в Postgres. Presence
остаётся источником событий, а время мы накапливаем рядом.

Второй нюанс: presence считает **соединения** (несколько вкладок = несколько
коннектов одного юзера). Время надо мерить на уровне **пользователя**: сессия
открывается, когда юзер стал online (первый коннект, `became_online=True`), и
закрывается, когда ушёл offline (последний коннект пропал,
`became_offline=True`). Это ровно то, что сейчас уже триггерит
`publish_user_presence_event`. То есть гранулярность «работал/не работал»
получаем бесплатно.

Третий нюанс — точность. WS-presence = «вкладка открыта», а не «человек
работает». Вкладку можно оставить на ночь. На Этапе 1 считаем по presence
(простое, честное «сессия онлайн»). На Этапе 3 (опционально) уточняем по
активности вкладки (focus/idle), если бизнесу нужна именно «активная работа».

## Модель данных

Новая таблица `work_sessions` (модуль — расширяем существующий `analytics`,
либо отдельный `worklog`; склоняюсь к `analytics`, там уже есть service/schemas):

| поле | тип | смысл |
|---|---|---|
| `id` | uuid PK | |
| `user_id` | uuid FK → users.id, `ON DELETE SET NULL`, nullable | по паттерну миграции 0011 (удаление юзера не блокируется) |
| `started_at` | timestamptz | момент `became_online` |
| `last_heartbeat_at` | timestamptz | обновляется каждый HB (раз в 30с) |
| `ended_at` | timestamptz null | NULL = сессия ещё открыта |
| `end_reason` | enum(`disconnect`,`sweep`,`server_shutdown`,`reconcile`) | как закрылась — для отладки/доверия к данным |
| `duration_seconds` | int null | денормализация для быстрых отчётов; считается при закрытии |

Индексы: `(user_id, started_at)`, частичный `WHERE ended_at IS NULL` (для
реконсиляции открытых сессий на старте).

Это новая alembic-миграция — следующий номер **0029** (последняя — 0028).

## Логика записи (где врезаемся в код)

Все хуки уже существуют, добавляем рядом вызовы в новый
`analytics/worklog_service.py`:

1. **Открытие сессии** — в `endpoints/realtime.py`, там где сейчас
   `if became_online: publish_user_presence_event(..., online=True)`.
   Рядом: `await worklog.open_session(user_id)` — INSERT с
   `started_at = last_heartbeat_at = now()`, `ended_at = NULL`.

2. **Heartbeat** — в `_heartbeat()`, рядом с `presence.heartbeat(...)`:
   `await worklog.touch(user_id)` — UPDATE `last_heartbeat_at = now()` у
   открытой сессии юзера. Это критично: по нему мы закроем «повисшие» сессии
   честным временем, а не временем обнаружения.

3. **Штатное закрытие** — в `finally`, где `if became_offline:
   publish_user_presence_event(..., online=False)`:
   `await worklog.close_session(user_id, reason="disconnect", at=now())`.

4. **Закрытие после падения воркера** — sweeper уже вызывает `on_offline(uid)`
   колбэк для каждого ставшего offline. Туда добавляем
   `worklog.close_session(uid, reason="sweep", at=last_heartbeat_at)`.
   **Важно:** закрываем по `last_heartbeat_at`, а не по «сейчас» — иначе в
   время засчитаются те ~90с TTL, что юзер уже был мёртв.

5. **Реконсиляция на старте** — в lifespan при старте процесса: все сессии с
   `ended_at IS NULL` закрываем по их `last_heartbeat_at` с
   `reason="server_shutdown"`. Это чинит случай, когда упал/перезапустился
   сам backend и `finally`/sweeper не отработали. После — сессии открываются
   заново по мере реконнекта WS.

`duration_seconds = ended_at − started_at` пишем при любом закрытии.

### Идемпотентность и гонки

- Открытие защищаем `became_online` (presence уже гарантирует, что это
  происходит один раз на «волну онлайна» юзера). Дополнительно — частичный
  unique-индекс «не больше одной открытой сессии на user_id»: `UNIQUE
  (user_id) WHERE ended_at IS NULL`, INSERT с `ON CONFLICT DO NOTHING`.
- Закрытие — `UPDATE ... WHERE user_id=? AND ended_at IS NULL`; повторный
  вызов просто ничего не затронет.
- worklog никогда не должен валить WS-коннект: все вызовы в try/except с
  логом (тот же принцип, что у presence.heartbeat в текущем коде).

## API и отчёты

Эндпоинты в `analytics` (OpenAPI — `docs/openapi.yaml`, фронт-типы
кодогенерятся через openapi-typescript):

- `GET /analytics/worklog/summary?from&to&userId?` → агрегаты: суммарное время
  по дням / по сотрудникам. Аккуратно с открытой сессией: к закрытым
  интервалам добавляем «хвост» текущей открытой сессии до `now()`.
- `GET /analytics/worklog/sessions?userId&from&to` → список сырых интервалов
  (для детального просмотра / аудита).
- Права: смотреть **своё** время — любой; чужое/всех — под право вроде
  `analytics:worklog_all` (по паттерну матрицы прав в `modules/permissions`).

Агрегацию по дням считаем с учётом перехода через полночь (длинную сессию
бьём по суткам в TZ компании). Часовой пояс — фиксированный конфигом
(Europe/Moscow), не из браузера, чтобы отчёты сходились у всех.

## Фронт

- Страница `/analytics` (или вкладка «Время») — таблица сотрудник × день,
  итоги за период, выбор диапазона дат. Переиспользуем FilterBar/FilterChip
  паттерн (см. память `crm-lg-filters`).
- В отчёте честно помечаем «онлайн-время по сессиям» как метрику, чтобы её не
  путали с «активной работой» (особенно до Этапа 3).
- Realtime не обязателен; страница тянет агрегаты по запросу.

## Этапы внедрения

**Этап 1 — MVP (онлайн-время по presence).**
Миграция 0029 + `worklog_service` + 5 хуков (open/touch/close/sweep/reconcile)
+ `GET /analytics/worklog/summary` + простая таблица на фронте. Уже даёт
рабочий ответ «сколько времени сотрудник был в CRM».

**Этап 2 — детализация и выгрузка.**
Эндпоинт `sessions`, экспорт в xlsx/csv, фильтры по сотруднику/периоду,
права `analytics:worklog_all`. Дашборд-вид при желании.

**Этап 3 — активность вместо «вкладка открыта» (опционально).**
Фронт шлёт heartbeat только когда вкладка в фокусе и не idle (нет ввода
N минут → пауза). Тогда `last_heartbeat_at` отражает реальную активность, а
длинные «забыл закрыть вкладку» интервалы не раздувают цифры. Метрику можно
разделить на «онлайн» и «активно».

## Тесты и проверка (обязательный шаг)

- Юнит на `worklog_service`: open→touch→close даёт корректный
  `duration_seconds`; повторный open/close идемпотентен.
- Сценарий sweep: открыли сессию, «уронили» воркер (нет disconnect), sweeper
  закрывает по `last_heartbeat_at` — длительность не включает TTL-хвост.
- Реконсиляция на старте закрывает повисшие `ended_at IS NULL`.
- Расширить `backend/tests/test_realtime_presence.py` связкой
  presence-событие → запись в `work_sessions`.
- Проверка агрегации через полночь и суммирования открытого «хвоста».

## Риски / на что обратить внимание

- **Точность ≠ табель учёта рабочего времени.** Это «время в системе», а не
  юридический учёт. Зафиксировать это в UI и при обсуждении с заказчиком.
- **Приватность.** Пер-минутный трекинг сотрудников — чувствительная тема;
  стоит ограничить видимость правами и предупредить команду.
- **Multi-worker.** Запись в Postgres процессо-безопасна (в отличие от старого
  in-memory presence), но реконсиляцию на старте должен делать каждый воркер
  только для «своих» — проще: закрывать по `last_heartbeat_at` старше порога
  (напр. > 2×TTL), чтобы один воркер не закрыл живую сессию другого. Уточнить
  при реализации.
- **In-memory fallback presence** (тесты/нет Redis) не шлёт heartbeat и не
  имеет sweeper — worklog в этом режиме закроет сессию только по disconnect.
  Для прод-конутра это не проблема (Redis есть), но в тестах учитываем.

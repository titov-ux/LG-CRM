# План: AI-скоринг соответствия кандидат ↔ вакансия

Статус: черновик плана. Дата: 2026-05-31.

## 1. Цель и сценарий

Дать рекрутёру быструю оценку «насколько кандидат подходит под вакансию» —
число 0–100 + разбивка по критериям + текстовый вердикт. Используется на канбане
вакансии (у каждого прикреплённого кандидата) и при подборе из базы (превью до
прикрепления). Скоринг помогает приоритизировать, кого вести в первую очередь, и
объясняет «почему», а не выдаёт чёрный ящик.

Подбор кандидатов под вакансию из всей базы (matchmaking/ранжирование пула) —
**реализован** поверх скоринга: `GET /vacancies/{id}/candidates/rank` ранжирует
подходящий пул по детерминированному `cheap_score` (мгновенно, бесплатно), а
тумблер «Уточнить ИИ» дообогащает верхние результаты оценкой релевантности от
LLM. Фронт — диалог `MatchCandidatesDialog` (кнопка «Подобрать» на карточке
вакансии). Логика подбора: `service.rank_candidates` (пул = тип сделки совпадает,
не архив, статус не финальный, ещё не прикреплён; cap пула 1000, cap обогащения 12).

## 2. Как ложится на текущую архитектуру

Переиспользуем то, что уже есть, без новых зависимостей:

- **Связка `VacancyCandidate`** (`modules/matching/models.py`) — уже хранит пару
  vacancy↔candidate с `UNIQUE(vacancy_id, candidate_id)`. Скор кладём прямо в неё:
  оценка — атрибут связки, а не кандидата/вакансии по отдельности.
- **Клиент `YandexGptClient.json_completion(system, user, schema_name, schema, max_tokens)`**
  (`integrations/yandex_gpt.py`) — тот же путь, что у парсинга вакансии и адаптации
  резюме. Ошибки уже типизированы: `AiUnavailableError` → 503, `AiBadRequestError`
  → 502, `AiTruncatedJsonError` → 413.
- **Хелперы `_candidate_brief` / `_vacancy_brief`** (`modules/candidates/resume_ai.py`) —
  уже сериализуют кандидата и вакансию в компактный текст для LLM. Их надо вынести
  в общий модуль (см. §4), чтобы скоринг и адаптация резюме делили один код.
- **Паттерн AI-эндпоинта** — как `POST /candidates/{id}/resume/improve`: try/except
  на три AI-ошибки, маппинг в 503/502/413.
- **Realtime** — после записи скора шлём событие в `EventBus`, фронт инвалидирует
  react-query кэш списка кандидатов вакансии (как в `crm-lg-realtime`).

## 3. Модель данных

Скор — это атрибут связки + кэш (дорого считать на каждый рендер). Добавляем поля
в `vacancy_candidates`, новой таблицы не заводим.

Новые колонки в `VacancyCandidate`:

| Колонка | Тип | Назначение |
|---|---|---|
| `ai_score` | `SmallInteger` nullable | Итог 0–100. NULL = ещё не считали |
| `ai_recommendation` | `Enum(match_recommendation)` nullable | `strong` / `good` / `weak` / `mismatch` |
| `ai_breakdown` | `JSONB` nullable | Разбивка по критериям (см. ниже) |
| `ai_summary` | `Text` nullable | 2–3 предложения вердикта на русском |
| `ai_strengths` | `JSONB` (массив строк) nullable | Сильные стороны под эту вакансию |
| `ai_gaps` | `JSONB` (массив строк) nullable | Чего не хватает / риски |
| `ai_scored_at` | `DateTime(tz)` nullable | Когда посчитали |
| `ai_model` | `String(64)` nullable | Модель (`yandexgpt/rc`) для воспроизводимости |
| `ai_input_hash` | `String(64)` nullable | SHA-256 от брифа кандидата+вакансии |

`ai_input_hash` — ключевая оптимизация: при повторном запросе, если хэш входа не
изменился (кандидат и вакансия не правились), отдаём кэш и не дёргаем LLM. На фронте
показываем бейдж «оценка устарела», если хэш разошёлся с текущими данными.

Структура `ai_breakdown` (JSONB):

```json
{
  "stack":      { "score": 80, "weight": 0.35, "note": "Есть Java/Spring, нет Kafka" },
  "grade":      { "score": 100, "weight": 0.20, "note": "Senior = Senior" },
  "experience": { "score": 70,  "weight": 0.20, "note": "5 лет при требуемых 6+" },
  "format":     { "score": 100, "weight": 0.15, "note": "Гибрид совпадает" },
  "rate":       { "score": 60,  "weight": 0.10, "note": "Ставка выше бюджета на 10%" }
}
```

Веса фиксируем в коде (не отдаём LLM решать вклад) — так число воспроизводимо и
объяснимо. LLM выставляет только `score` и `note` по каждому критерию, а итоговый
`ai_score` считаем на бэкенде как взвешенную сумму. Это гибрид: детерминированная
арифметика поверх качественной оценки модели.

Миграция: alembic `00XX_match_ai_scoring` — добавить колонки + `ENUM match_recommendation`.
Все nullable, дефолтов на бэкап не требуется.

## 4. Бэкенд: новый модуль `modules/matching/ai.py`

Зеркало `vacancies/ai.py` и `candidates/resume_ai.py`.

Шаги:

1. **Вынести брифы в общий модуль.** Переместить `_candidate_brief` и
   `_vacancy_brief` из `candidates/resume_ai.py` в `modules/candidates/briefs.py`
   (или `core/ai_briefs.py`), оставив реэкспорт в `resume_ai.py` ради обратной
   совместимости. Скоринг импортирует их же — единый формат входа для всех AI-фич.

2. **Детерминированный пре-скоринг (быстрый путь, без LLM).** Функция
   `cheap_score(candidate, vacancy)` считает то, что считается без модели:
   - пересечение стека (set candidate.stack ∩ vacancy.stack / |vacancy.stack|);
   - дистанция грейда (Junior<Middle<Senior<Lead → 0/33/66/100);
   - формат работы (совпадает/нет);
   - ставка vs бюджет (rate_month «на руки» против rate_client — переиспользовать
     логику `lib/compensation.ts`-аналога, см. память `crm-lg-margin-net`).

   Этот результат всегда доступен мгновенно и служит фоллбэком, если AI выключен
   (нет ключа / 503). Возвращаем тот же контракт, но `ai_summary = null`,
   `ai_recommendation` выводим из числа порогами.

3. **`SCORE_SCHEMA`** (json_schema для `json_completion`) — модель возвращает по
   каждому критерию `score` (0–100) + `note`, плюс `strengths[]`, `gaps[]`,
   `summary`. Итоговое число НЕ просим у модели — считаем сами.

4. **`_SYSTEM_PROMPT`** — роль «ассистент рекрутингового агентства», правила:
   оценивать строго по предоставленным брифам, не выдумывать факты, отвечать
   по-русски, быть конкретным в `note` (что именно совпало/не совпало).

5. **`async def score_match(candidate_dict, vacancy_dict) -> MatchScore`** —
   собирает брифы, режет по `yandex_ai_max_input_chars`, зовёт
   `json_completion(..., max_tokens=1500)`, нормализует ответ (`_coerce_*` как в
   `vacancies/ai.py`), накладывает фиксированные веса → итоговый `ai_score`,
   считает `ai_input_hash`. Бросает типизированные AI-ошибки наверх.

Контракт ответа (DTO `MatchScoreResponse`, camelCase) добавляем в
`matching/schemas.py`: `score`, `recommendation`, `breakdown`, `summary`,
`strengths`, `gaps`, `scoredAt`, `model`, `stale` (вычисляемое: хэш разошёлся).

## 5. Бэкенд: эндпоинты

В `api/v1/endpoints/matching.py`:

- **`POST /matches/{match_id}/score`** — посчитать/пересчитать для прикреплённой
  связки. Параметр `?force=true` игнорирует кэш по хэшу. Возвращает
  `MatchScoreResponse`. Пишет результат в связку, шлёт WS-событие.
- **`GET /matches/{match_id}/score`** — отдать сохранённый скор (или 404, если
  ещё не считали) + флаг `stale`. Лёгкий, без LLM.
- **`POST /vacancies/{id}/candidates/score`** — батч: посчитать всех прикреплённых,
  у кого нет скора или он `stale`. Под капотом — последовательно (или с малым
  семафором, лимиты YandexGPT). Возвращает список результатов + сводку «посчитано N,
  из кэша M, ошибок K». Частичный успех не валит весь запрос.
- **`POST /vacancies/{id}/score-candidate`** body `{ candidateId }` — превью-скор
  БЕЗ прикрепления и без записи в БД (для подбора из `/database`). Только считает и
  отдаёт.

Обработка ошибок: `AiTruncatedJsonError` → 413 `input_too_long`, `AiBadRequestError`
→ 502 `ai_bad_request`. **Реализовано иначе, чем 503 в исходном наброске:**
`AiUnavailableError` НЕ возвращает 503 — вместо этого сервис делает graceful-
фоллбэк на детерминированный `cheap_result` и возвращает 200 с `aiEnriched: false`
и `model: 'cheap'`. Так чип всегда показывает осмысленную оценку, а не ошибку.
Хэш входа при cheap-фоллбэке НЕ сохраняется (`ai_input_hash = NULL`) — следующий
POST повторит попытку LLM, как только AI снова доступен. Превью-эндпоинт ведёт
себя так же. (Реализация: `service.score_and_store`, `api/v1/endpoints/matching.py`.)

## 6. Фронтенд — чип в строке прикреплённого кандидата

Основное (и единственное обязательное на Этапе 1–2) место — **строка прикреплённого
кандидата** в карточке вакансии. Это компонент
`frontend/src/features/matching/MatchCompensationRow.tsx`, который рендерится списком
в `VacancyCardPage` (секция «Прикреплённые кандидаты · N»). Карточек на отдельном
канбане не трогаем — скор живёт там, где рекрутёр уже работает со связкой.

### 6.1. Сам чип (в правом блоке строки)

В `MatchCompensationRow` справа уже есть блок `flex shrink-0 items-center gap-2`
с `MarginBadge` и меню резюме. **AI-чип встаёт первым в этом блоке, слева от
`MarginBadge`** — порядок «скор → маржа → резюме → открепить».

Новый компонент `features/matching/AiScoreBadge.tsx`. Состояния:

- **Есть скор** — пилюля `<иконка sparkles> 87`. Цвет по `recommendation`:
  `strong` (≥75) — teal/зелёный, `good` (50–74) — amber, `weak` (25–49) — серый,
  `mismatch` (<25) — красный. Тон фон/текст из палитры (как `MarginBadge`).
- **`stale`** (хэш входа разошёлся с текущими данными) — к пилюле добавляем
  бледный значок `clock`/точку и `title="Данные изменились — пересчитайте"`.
- **Не считали** (`score === null`) — вместо пилюли маленькая кнопка-призрак
  «Оценить» с иконкой sparkles (как кнопка адаптации резюме в этой же строке).
- **Идёт расчёт** — `Loader2 animate-spin` на месте пилюли (тот же паттерн, что
  `improvingCandidateId` в `VacancyCardPage`).

Клик по чипу/кнопке: если скора нет — дёргает `POST /matches/{id}/score`; если есть
— раскрывает разбивку (см. 6.2). Клик по `clock` у `stale` — `?force=true`.

### 6.2. Разбивка — раскрытие под строкой

Разбивку показываем **инлайн-раскрытием прямо под строкой** (а не Popover) — строки
лежат в обычном списке, места хватает, и это надёжнее, чем Popover (нет грабли с
`pointer-events`/`z-index` внутри Sheet, память `crm-lg-popover-in-sheet`). Если
позже понадобится из Sheet — Popover тоже годится, но дефолт — раскрытие.

Содержимое раскрытия: итоговое число + «N/100 · вердикт», справа значок «устарело»
если stale; строки критериев (Стек/Грейд/Опыт/Формат/Ставка) с прогресс-баром,
весом и `note`; ниже summary; кнопка «Пересчитать» (`?force=true`). Сильные стороны
и пробелы (`strengths`/`gaps`) — списками, если заполнены. Визуал — как в мокапе,
который я показал в чате.

### 6.3. Хук и данные

Новый хук `features/matching/hooks.ts → useScoreMatch()` (мутация) и
`useMatchScore(matchId)` (чтение, lazy — только при раскрытии). Скор приходит вместе
со списком прикреплённых: либо расширяем существующий ответ `/vacancies/{id}/candidates`
полями `aiScore`/`aiRecommendation`/`aiScoredAt`/`aiStale` (дёшево, чип рисуется без
доп. запроса), либо отдельным `GET`. Предпочтительно — первое: чип виден сразу при
открытии вакансии, разбивку грузим по клику.

### 6.4. Realtime и оптимистичность

По WS-событию `match.scored` инвалидируем кэш списка прикреплённых (react-query),
чип перерисовывается. На время расчёта — оптимистичный спиннер; echo-suppress через
`X-Client-Id` (память `crm-lg-realtime`).

### 6.5. AI недоступен

При 503 показываем детерминированный `cheap_score` с приглушённым тоном и `title`
«оценка без AI» — без красной ошибки. Чип остаётся информативным.

### 6.6. Этап 3 (реализовано)

- «Оценить всех» в шапке секции → `POST .../candidates/score` (батч) — готово.
- Сортировка «по AI-оценке» + фильтр «только подходящие» (strong/good) над списком
  прикреплённых — готово (локальный тулбар в `VacancyCardPage`).
- Превью-скор до прикрепления (`AiPreviewBadge` + `useScorePreview`,
  `POST .../candidates/score-preview`): в `AttachCandidateDialog` и на `/database`
  под выбранную из пикера вакансию — готово.
- Кодоген типов из OpenAPI (`openapi-typescript`, память `crm-lg-api-transition`) —
  не сделано: фронт-типы пока заданы вручную в `api/types.ts`; нужно дописать
  эндпоинты в `docs/openapi.yaml` и перегенерировать `types.gen.ts`.

## 7. Realtime, права, наблюдаемость

- **Realtime**: новое WS-событие `match.scored` (payload: matchId, vacancyId,
  candidateId, score, recommendation). Фронт инвалидирует кэш списка кандидатов
  вакансии. Echo-suppress через `X-Client-Id` (память `crm-lg-realtime`).
- **Права**: действие `match:score` (кто может запускать скоринг — рекрутёр+).
  Чтение скора — у всех, кто видит связку. Добавить в `modules/permissions`.
- **Метрики/логи** (реализовано в `modules/matching/metrics.py`): in-process
  счётчики `SCORING_METRICS` (cache_hits / llm_calls / cheap_fallbacks / errors +
  средняя латентность LLM) и структурные лог-события (`scoring.cache_hit`,
  `scoring.llm_ok`, `scoring.cheap_fallback`, `scoring.error`) для агрегации в
  логовом пайплайне / Sentry. Подключено в `service.score_and_store`.
- **Стоимость/лимиты**: батч-скоринг с семафором, кэш по `ai_input_hash`, чтобы не
  жечь токены на неизменных данных. Учесть единый риск отвала AI на prod+staging
  при минусе по балансу YC (память `crm-lg-ai-keys-billing`).

## 8. Тесты

- Unit: `_coerce_*` нормализация ответа LLM (мусорные/частичные JSON),
  взвешенная сумма → `ai_score`, `cheap_score` на крайних случаях (пустой стек,
  Lead vs Junior), вычисление `ai_input_hash` и детект `stale`.
- API: 200 + запись в связку, кэш-хит по хэшу (LLM не вызывается — мок),
  `force=true` пересчитывает, 503 при отсутствии ключа отдаёт фоллбэк-контракт,
  413 на слишком длинном бизнес-входе, 404 на чужом match_id.
- Батч: частичный успех (один кандидат падает — остальные считаются).
- e2e (как в чате/календаре): прикрепить кандидата → оценить → бейдж и поповер.

## 9. Этапы

1. **Этап 1 — модель + детерминированный скоринг.** Миграция, колонки, `cheap_score`,
   `GET/POST /matches/{id}/score` без LLM (только арифметика), бейдж на фронте.
   Уже полезно и не зависит от AI.
2. **Этап 2 — LLM-слой.** `matching/ai.py`, `SCORE_SCHEMA`, вынос брифов, гибрид
   (веса на бэке), кэш по хэшу, поповер с разбивкой, фоллбэк на cheap при 503.
3. **Этап 3 — батч + превью.** «Оценить всех», превью-скор в `/database`,
   сортировка/фильтр по скору, WS-событие `match.scored`, метрики.

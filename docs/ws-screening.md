# WebSocket AI-скрининга: `/api/v1/ws/screening/{sessionId}`

Живой канал комнаты скрининга: браузер рекрутера шлёт PCM-аудио двух каналов,
сервер отдаёт транскрипт, обновления чек-листа вопросов и подсказки AI-агента.

В `docs/openapi.yaml` этой ручки нет и не будет: OpenAPI описывает HTTP-запросы,
а не поток фреймов после Upgrade. Источник истины для протокола — этот файл и
код: `backend/app/api/v1/endpoints/screening_ws.py` (сервер),
`frontend/src/features/screening/useScreeningSocket.ts` (единственный клиент),
`backend/app/modules/screening/stt_bridge.py` + `services/stt/server.py`
(плечо backend → stt-service).

---

## 1. Подключение и авторизация

```
wss://<host>/api/v1/ws/screening/<sessionId>?token=<access JWT>
```

- Токен передаётся **в query**, а не в заголовке: браузерный `WebSocket` не
  умеет ставить `Authorization` при handshake. Это же делает `/api/v1/ws/events`.
- Принимается только **access**-токен (`type=access` в payload); пользователь
  должен быть активен.
- Дополнительно проверяются:
  - право `screening:run` (матрица прав, `permissions_service.user_has_action`);
  - роль в сессии: вести стрим может **ведущий рекрутер** сессии или **admin**;
  - статус сессии — строго `live` (`screening_ws.py`): в `draft` встреча ещё не
    начата, в `processing` / `done` / `error` стримить нечего.
- Токен живёт `ACCESS_TOKEN_TTL_MINUTES` (по умолчанию 15 мин), а встреча — до
  `SCREENING_MAX_DURATION_MIN` (90 мин). Проверка токена делается **только при
  подключении**: уже открытый сокет не рвётся из-за протухшего токена, но при
  любом реконнекте клиент обязан взять свежий access (см. код `4001` ниже).

Прокси: nginx проксирует `/api/v1/ws/` c `Upgrade`-заголовками и
`proxy_read_timeout 7200s` (> 90 мин hard-stop) — см. `infra/nginx.example.conf`.

## 2. Клиент → сервер

### 2.1. Control-сообщения (текстовые фреймы, JSON)

| Сообщение | Когда шлёт клиент | Что делает сервер |
|---|---|---|
| `{"type":"start","sampleRate":16000}` | сразу после `open` | подтверждает состояние: `session.state {status:"live", sttReady}` |
| `{"type":"stop"}` | нажата «Завершить встречу» | просит STT дожать хвосты (`flush`), шлёт `session.state {status:"stopping"}` и закрывает соединение |
| `{"type":"pong"}` | в ответ на серверный `ping` | подтверждение живого клиента |

Неизвестные типы и не-JSON текст молча игнорируются — соединение не рвётся.

Важно про `stop`: без него последняя реплика теряется. В stt-service открытый
VAD-регион ждёт паузы `MIN_SILENCE_MS`; если встречу закрыли сразу после фразы,
этой паузы нет, и только `stop` (или закрытие моста) её финализирует. При этом
`stop` — «терминальный» жест: он рвёт STT-мост, поэтому обычный размонтаж
компонента его НЕ шлёт (иначе dev StrictMode рвал бы мост на каждом mount).

### 2.2. Бинарный фрейм (аудио)

```
[0]      : u8  — канал: 0 = рекрутер (микрофон), 1 = кандидат (звук вкладки)
[1..]    : PCM16LE, 16 000 Гц, mono — ~100 мс аудио (1600 сэмплов = 3200 байт)
```

- Полный кадр — **3201 байт**. Ресемплинг до 16 кГц делает AudioWorklet на
  клиенте (`frontend/src/features/screening/audioCapture.ts`, `chunk = 1600`).
- Каналы идут в одном соединении и распознаются независимо — так получается
  разделение спикеров без диаризации.
- Фреймы короче 2 байт и с неизвестным номером канала stt-service отбрасывает;
  нечётная длина PCM-части считается битым кадром (пропускается, соединение
  живёт).
- Потолок размера фрейма — **4 МБ**: флаг uvicorn `--ws-max-size 4194304`
  (`infra/docker-compose.prod.yml`) и симметричный `max_size=2**22` в
  `SttBridge`. nginx размер фреймов не ограничивает.
- Backpressure: если очередь к STT переполнена, backend выбрасывает кадры и
  считает их в `screening_stt_frames_dropped_total` — в транскрипте появится
  дыра, аудиозапись в S3 при этом полная.

## 3. Сервер → клиент

Все события — текстовые фреймы JSON. Отправка идёт через одну очередь и одну
задачу-отправителя: конкурентные `send_json` на одном ASGI-соединении
переплетают фреймы, поэтому порядок событий гарантирован.

### `hello` — первое сообщение после accept

```json
{ "type": "hello", "sessionId": "uuid", "lastSeq": 42,
  "sttReady": true, "maxDurationSec": 5400 }
```

- `lastSeq` — номер последнего сохранённого в БД сегмента. После реконнекта
  клиент сравнивает его со своим максимумом и дозагружает пропуск по REST
  (`GET /api/v1/screenings/{id}/segments`).
- `sttReady=false` — `STT_URL` пуст или мост не поднялся: комната работает,
  запись идёт, живого текста не будет.
- `maxDurationSec` = `SCREENING_MAX_DURATION_MIN × 60`.

### `transcript.partial` — черновик текущей фразы

```json
{ "type": "transcript.partial", "speaker": "recruiter", "text": "…" }
```

Не имеет `seq`, в БД не пишется, перезаписывается следующим `partial` и
гасится приходом `final` этого же спикера. При обрыве соединения клиент
сбрасывает висящие partial-ы.

### `transcript.final` — сохранённый сегмент

```json
{ "type": "transcript.final", "seq": 43, "speaker": "candidate",
  "text": "…", "startedMs": 12000, "endedMs": 15400, "latencyMs": 1800 }
```

- `seq` — сквозной возрастающий номер сегмента в сессии; по нему клиент
  дедуплицирует (после реконнекта одно и то же может прийти дважды).
- `startedMs`/`endedMs` — смещения от начала аудиопотока канала, не wall-clock.
- `latencyMs` — задержка распознавания, из неё считается p95 в `/metrics`.
- Сегменты, отсеянные фильтрами (дубль/эхо, галлюцинация Whisper) и события
  после ухода сессии из `live` клиенту не отправляются вовсе.

### `questions.updated` — чек-лист после тика AI-агента

```json
{ "type": "questions.updated", "questions": [ { "id": "...", "position": 0,
  "text": "...", "goal": null, "source": "pregenerated|followup",
  "status": "pending|asked|answered|skipped", "answerSummary": null } ] }
```

Полный актуальный список вопросов (не дельта) — клиент заменяет им состояние
карточки сессии.

### `hint` — короткая подсказка рекрутеру

```json
{ "type": "hint", "text": "Уточните опыт с Kubernetes" }
```

Эфемерна: не хранится, показывается последние несколько штук.

### `session.state` — смена состояния потока

```json
{ "type": "session.state", "status": "live",
  "sttReady": false, "error": "stt_unavailable" }
```

- `status`: `live` (в т.ч. ответ на `start` и уведомления о смене `sttReady`),
  `stopping` (принят `stop`), `processing` (сработал hard-stop по длительности).
- `error` (опционально): `stt_unavailable` — мост не поднялся;
  `stt_disconnected` / `stt_closed` — мост умер; `busy` — stt-service упёрся в
  `STT_MAX_SESSIONS`; `max_duration` — встреча закрыта по лимиту.
- Падение STT **не** рвёт соединение с рекрутером: супервизор переподключает
  мост в фоне и присылает `session.state {sttReady:true}` после починки —
  поэтому баннер в UI нужно снимать по этому же событию.

### `ping` / `pong`

```json
{ "type": "ping" }
```

Сервер шлёт `ping` каждые 30 с, клиент отвечает `{"type":"pong"}`. Это не
WebSocket-фреймы протокольного ping/pong, а обычные JSON-сообщения: браузерный
API не даёт ни отправлять, ни наблюдать контрольные фреймы. Клиент дополнительно держит
watchdog: если от сервера ничего не приходило дольше ~50 с, соединение считается
полуоткрытым (NAT/усыпление ноутбука) — сокет рвётся руками и уходит в реконнект.

Параллельно, каждые 15 с, сервер обновляет отметку активности сессии в БД: по
ней уборщик (`screening.close_stale_sessions`) отличает «клиент жив, просто
молчит» от «рекрутер закрыл вкладку» (`SCREENING_ORPHAN_GRACE_MIN`).

## 4. Коды закрытия

| Код | Значение | Что делает клиент |
|---|---|---|
| **4001** | Токен отсутствует, невалиден или протух (в т.ч. не-access токен, заблокированный пользователь) | обновить access-токен и переподключиться; повторять ограниченное число раз, чтобы не зациклиться на «вечно плохом» токене |
| **4003** | Соединение **вытеснено** новым подключением этой же сессии (вторая вкладка/устройство) | НЕ переподключаться: реконнект вызовет бесконечный «пинг-понг» двух вкладок. Показать «встреча продолжена в другой вкладке» |
| **1008** | Нет прав (`screening:run`, не ведущий рекрутер) либо статус сессии не `live` | терминально: реконнект не поможет. Перечитать карточку сессии и обновить UI |
| 1000 | Штатное закрытие после `stop` или после `session.state {error:"max_duration"}` | не переподключаться |
| 1006 и прочие | Сеть/прокси/рестарт backend | реконнект с экспоненциальным backoff и джиттером |

Историческая деталь: до появления 4003 вытеснение закрывалось кодом **1012**;
клиент обрабатывает его так же, как 4003, — это нужно на время выката, когда
фронт и бэк разных версий.

## 5. Одно соединение на сессию

Реестр активных сокетов (`_ACTIVE_SOCKETS`) и «припаркованных» STT-мостов
(`_LINGERING_BRIDGES`) живут **в памяти процесса backend**. Отсюда два
следствия:

1. Новое подключение к той же сессии закрывает предыдущее кодом 4003 —
   иначе два писателя сегментов дублируют реплики в транскрипте.
2. Backend в проде запускается с `--workers 1`. При нескольких воркерах
   реестры расщепляются: вытеснение перестаёт работать, а мост не находится
   при реконнекте. Подробности и условия возврата 2+ воркеров — в комментарии
   к сервису `backend` в `infra/docker-compose.prod.yml`.

## 6. Реконнект

Что сервер обещает клиенту при обрыве:

- **STT-мост живёт ещё `SCREENING_WS_HOLD_SEC`** (по умолчанию 60 с) и
  переиспользуется тем же `sessionId` — контекст распознавания и место в пуле
  `STT_MAX_SESSIONS` не теряются. Мост НЕ паркуется, если ушёл `stop` или
  сработал hard-stop.
- **Сессия остаётся `live`** — статус не меняется от того, что вкладка моргнула.
  Совсем «осиротевшую» сессию закроет beat-уборщик через
  `SCREENING_ORPHAN_GRACE_MIN` минут без активности.
- **Ничего не теряется в транскрипте на стороне БД**: сегменты пишутся по мере
  готовности, `hello.lastSeq` после реконнекта позволяет дозагрузить пропуск.

Что должен делать клиент (так и делает `useScreeningSocket.ts`):

1. Реконнект с экспоненциальным backoff и джиттером, потолок ~30 с; запрещён
   при кодах 4003 и 1008, при `max_duration` и после явного `stop()`.
2. Копить PCM в кольцевом буфере (~2 с) пока сокет не `OPEN`, и дослать его
   после `open` — иначе в транскрипте будет дыра ровно на время обрыва.
3. По `hello.lastSeq` дозагрузить пропущенные сегменты через
   `GET /api/v1/screenings/{id}/segments` и слить их по `seq`.
   Эта ручка доступна ведущему рекрутеру и админу без права
   `screening:view_report` — иначе дозагрузка ломалась бы прямо во время
   интервью; посторонним нужно `screening:view_report`.
4. Гасить partial-ы при обрыве: недоговорённая фраза после реконнекта не
   придёт, иначе она висит в UI вечно.

## 7. Лимиты и таймауты (сводка)

| Параметр | Значение по умолчанию | Где задаётся |
|---|---|---|
| Максимальная длительность встречи | 90 мин | `SCREENING_MAX_DURATION_MIN` |
| Окно переиспользования STT-моста | 60 с | `SCREENING_WS_HOLD_SEC` |
| Закрытие «осиротевшей» live-сессии | 15 мин без активности | `SCREENING_ORPHAN_GRACE_MIN` |
| Серверный `ping` | 30 с | константа в `screening_ws.py` |
| Обновление отметки активности | 15 с | константа в `screening_ws.py` |
| Переподключение к STT | каждые 5 с | константа в `screening_ws.py` |
| Максимальный размер WS-фрейма | 4 МБ | `--ws-max-size` у uvicorn |
| `proxy_read_timeout` на WS-локации | 7200 с | `infra/nginx.example.conf` |
| Параллельных встреч на stt-service | 8 | `STT_MAX_SESSIONS` (при переполнении — close 1013 + `error:busy`) |

Диагностика инцидентов — `docs/runbook.md` §8; метрики — `GET /metrics`
и `infra/alerts/screening.rules.yml`.

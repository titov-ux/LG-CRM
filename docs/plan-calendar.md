# План фичи «Календарь собеседований»

Статус: черновик к реализации · Дата: 2026-05-30 · Стартовая миграция: `0023`

## 1. Цель и scope

Дать рекрутеру назначать собеседования с кандидатами, видеть их в календаре и
**отмечать результат** (состоялось / не пришёл / отменено + исход). События
привязаны к кандидату, вакансии и связке `vacancy_candidates`, чтобы статус
собеса автоматически двигал канбан и кормил аналитику.

**MVP (этот документ):**
- сущность «событие» с типом `interview`, привязка к кандидату/вакансии/связке;
- участники (рекрутеры/пользователи), время, длительность, формат (онлайн/офис), ссылка/адрес;
- статус и исход события; при «состоялось» — запись фидбэка в `vacancy_candidates.feedback`;
- страница «Календарь» (месяц/неделя/день + список), создание из карточки кандидата и с канбана вакансии;
- уведомления участникам + realtime-обновление; напоминание до начала.

**Вне MVP (v2, раздел 9):** внешняя синхронизация (Google/Outlook/CalDAV), экспорт `.ics`, переговорки/ресурсы, повторяющиеся события.

## 2. Модель данных

Новый модуль `backend/app/modules/calendar/`. Делаем generic-таблицу событий с
типом, чтобы позже переиспользовать под встречи/напоминания, но MVP наполняет только `interview`.

### `calendar_events`
| поле | тип | примечание |
|---|---|---|
| `id` | uuid pk | `uuid_generate_v4()` |
| `type` | enum `event_type` | `interview` \| `meeting` \| `reminder` (MVP: interview) |
| `title` | text | автозаполняется «Собес: ФИО — Вакансия», редактируемо |
| `starts_at` | timestamptz | индекс |
| `ends_at` | timestamptz | `starts_at + duration`; nullable |
| `all_day` | bool | default false |
| `location_kind` | enum `event_location` | `online` \| `onsite` \| `phone` |
| `location` | text null | ссылка на встречу или адрес |
| `status` | enum `event_status` | `scheduled` \| `held` \| `no_show` \| `canceled` (default `scheduled`) |
| `outcome` | text null | заметка по итогу собеса |
| `candidate_id` | uuid fk → candidates | `SET NULL`, index |
| `vacancy_id` | uuid fk → vacancies | `SET NULL`, index |
| `match_id` | uuid fk → vacancy_candidates | `SET NULL`, index — ключевая связка |
| `created_by_id` | uuid fk → users | `SET NULL` |
| `created_at` / `updated_at` | timestamptz | `TimestampsMixin` |

### `calendar_event_attendees`
| поле | тип | примечание |
|---|---|---|
| `event_id` | uuid fk → calendar_events | `CASCADE` |
| `user_id` | uuid fk → users | `CASCADE` |
| `response` | enum `attendee_response` | `invited` \| `accepted` \| `declined` (default `invited`) |
| UNIQUE | `(event_id, user_id)` | |

Enum-ы оформляем по образцу `MatchStatus` (`values_callable=_enum_values`).
Миграция `0023_calendar_events.py`. FK на `users.id` — `SET NULL` + nullable,
консистентно с миграцией `0011` (удаление юзера не блокируется).

## 3. Связь с канбаном и аналитикой

- Создание `interview`-события на связке `match_id` → если у связки статус раньше `submitted/reviewed`, переводим в `interview` (через существующий `matching.service.update_match`, чтобы сработали уведомления и realtime).
- Отметка события `held` с исходом → опционально предложить следующий статус связки (`offered` / `rejected_client`) и записать `outcome` в `vacancy_candidates.feedback`.
- `no_show` / `canceled` сам по себе канбан не двигает, но виден в аналитике «attention» как сигнал.
- Аналитика: добавить в `analytics.service` метрику «собеседований за период» и «no-show rate» (отдельная карточка; переиспользует `Period`/`_count_by_bucket`).

## 4. API (OpenAPI + endpoints)

Эндпоинты в `backend/app/api/v1/endpoints/calendar.py`, схемы в модуле,
обязательно дописать в `docs/openapi.yaml` (фронт генерит типы через openapi-typescript).

| метод | путь | назначение |
|---|---|---|
| `GET` | `/calendar/events?from&to&recruiterId&vacancyId&candidateId&status&type` | список в диапазоне дат (для сетки/списка) |
| `POST` | `/calendar/events` | создать (title опционален → автогенерация) |
| `GET` | `/calendar/events/{id}` | детально + attendees |
| `PATCH` | `/calendar/events/{id}` | время/место/участники/перенос |
| `POST` | `/calendar/events/{id}/outcome` | отметить `held/no_show`, передать `outcome`, опц. `nextMatchStatus` |
| `POST` | `/calendar/events/{id}/cancel` | отмена с причиной |
| `DELETE` | `/calendar/events/{id}` | удалить (право `event:delete`) |

`GET` по диапазону отдаёт «толстые» элементы (вложенные `candidate`/`vacancy`
кратко), чтобы сетка не делала N запросов — в духе perf-паттернов проекта.

## 5. Права (permissions)

В `permissions/defaults.py` добавить действия и раздать по дефолтным ролям:
- `event:create`, `event:edit` — рекрутер и выше;
- `event:set_outcome` — рекрутер (своё) / лид (любое);
- `event:delete` — лид/админ.

Видимость: рекрутер видит события, где он участник или ответственный по вакансии;
лид/админ — все. Фильтрацию делаем в сервисе по тем же правилам, что и доступ к вакансиям.

## 6. Уведомления и realtime

- Расширить `NotificationEntityType` значением `event`; использовать `NotificationKind.status_change`/`system`.
- Триггеры: приглашение на событие, перенос/отмена, отметка исхода, напоминание (за 30 мин — настраиваемо).
- Реалтайм: новый тип в `realtime/events.py` (`calendar.event.created/updated/canceled`), инвалидация react-query ключей календаря; echo-suppress через `X-Client-Id` как в чате/канбане.
- Напоминания: лёгкий фоновый свипер в `lifespan` (как presence-sweeper) — раз в минуту ищет события с `starts_at` в окне и неотправленным `reminder_sent`. Доп. поле `reminder_sent_at timestamptz null` в таблице.

## 7. Frontend

Модуль `frontend/src/features/calendar/` (заменяет текущую заглушку `CalendarPage.tsx`).

- **Сетка:** месяц / неделя / день + режим «список». Библиотека — без тяжёлых зависимостей: собственная неделя/день-сетка на CSS-grid, либо `@fullcalendar/react` если согласимся на вес. По умолчанию — своя лёгкая сетка в Notion-эстетике.
- **FilterBar** (переиспользуем общий паттерн `FilterBar/FilterChip` + zustand-стор): рекрутер, вакансия, статус, тип.
- **Создание собеса:**
  - из карточки кандидата (`candidates.$id`) — кнопка «Назначить собес» (предзаполняет кандидата, выбор вакансии из его связок);
  - со строки кандидата на канбане вакансии — предзаполняет `match_id`, вакансию, кандидата;
  - с самого календаря — клик по слоту.
  - Форма в `Sheet` с дейтпикером — учесть фикс `crm-lg-popover-in-sheet` (PopoverContent: `pointer-events-auto` + `z-[60]`).
- **Карточка события:** время, участники с их `response`, кнопки «Состоялось / Не пришёл / Отменить», поле исхода, быстрый переход к кандидату/вакансии.
- **Точки входа в навигации:** пункт «Календарь» уже есть; добавить бейдж «сегодня N собесов» на дашборде.

Типы — из сгенерированного OpenAPI-клиента, ручные дубли не плодим.

## 8. Этапы внедрения

1. **Этап 1 — модель и API.** Миграция `0023`, модуль `calendar`, CRUD-эндпоинты, OpenAPI, юнит-тесты сервиса. Без UI.
2. **Этап 2 — базовый UI.** Сетка месяц/неделя + список, создание/редактирование события, фильтры. Привязка к кандидату/вакансии.
3. **Этап 3 — связка с канбаном.** Авто-перевод связки в `interview`, отметка исхода → `feedback` + предложение следующего статуса.
4. **Этап 4 — уведомления и realtime.** Инвайты, перенос/отмена, WS-инвалидция, свипер напоминаний.
5. **Этап 5 — аналитика.** Карточки «собесов за период» и «no-show rate», виджет «сегодня» на дашборде.
6. **Этап 6 — полировка и e2e.** Тесты Playwright (создание → отметка → проверка канбана), пустые состояния, права.

## 9. v2 — внешняя синхронизация

- Экспорт `.ics` на событие и подписной фид (read-only) для импорта в любой календарь — самый дешёвый первый шаг.
- Двусторонний синк Google Calendar / Microsoft 365 через OAuth (переиспользуем паттерн per-user токенов из `0021/0022`).
- Переговорки/ресурсы, повторяющиеся события (RRULE), часовые пояса на пользователя.

## 10. Тесты

- **Бэк:** сервис (создание двигает связку; outcome пишет feedback; права видимости; коллизия слота — предупреждение, не блок), эндпоинты, миграция применяется/откатывается. Закрываем дефицит покрытия бэка.
- **Фронт:** e2e сценарий «назначил собес из карточки → виден в сетке → отметил `held` → связка в `interview`/`offered`».

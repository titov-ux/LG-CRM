# Perf-итерация — 30 мая 2026

Заход: 3 экрана (канбан вакансий, канбан/база кандидатов, карточка кандидата).
Цель — сократить серверный отклик и видимое время до интерактивности.

## TL;DR

Найдено **2 баги** (тихая обрезка канбана при >50 записей) и **5 узких мест**
в бэкенде. Поправлено всё, добавлены недостающие индексы, на фронте включены
prefetch на hover, memo для карточек и устранён ложный «N+1 на клиенте» на
карточке вакансии. Полный protocol замера ниже.

## Что было сломано (и поправлено)

### B1. Канбан кандидатов — потолок 50

`CandidatesKanbanPage` вызывал `useCandidates({archived:false})` без `pageSize`.
Дефолт бэка — `pageSize=50`. Любая команда с >50 активных кандидатов видела
только первые 50 в порядке (status, kanban_order, created_at desc) — остальные
тихо исчезали с доски.

Фикс: явный `pageSize: 200` + комментарий. Тот же фикс на `VacanciesKanbanPage`.
Следующий шаг (если 200 окажется мало) — стрим по колонкам.

### B2. Карточка вакансии: in-memory filter по 50 кандидатам

`VacancyCardPage` тянул `useCandidates()` (тоже 50) и фильтровал прикреплённых
в `(items).filter(c => c.vacancyIds.includes(vacancy.id))`. На больших базах
прикреплённые к вакансии кандидаты пропадали из списка.

Фикс — серверный фильтр:

* в `list_candidates` добавлен `vacancy_id` параметр → `EXISTS` на
  `vacancy_candidates` (использует индекс `(candidate_id)`);
* фронт зовёт `useCandidates({ vacancyId, pageSize: 200 })`.

## Узкие места бэкенда (поправлены)

### P1. `reorder_kanban`: `db.refresh()` в цикле

После `db.commit()` шёл цикл `for c in rows: await db.refresh(c)`. Батч drag-n-drop
из 20 карточек = 20 лишних SELECT'ов **после** транзакции. Удалено — все поля,
которые мы меняли (status / status_changed_at / kanban_order), уже в инстансах,
триггеров на стороне БД нет. Тот же фикс на вакансиях.

### P2. Пересчёт `kanban_order` через выборку всей колонки

`create_candidate`, `change_status` (кандидаты и вакансии), `create_vacancy` —
все четыре места делали `SELECT * FROM ... WHERE status=...` только чтобы
вычислить `max(kanban_order) + 1`. На колонке в 500+ карточек это до 50мс
лишних. Заменено на `SELECT max(kanban_order) WHERE status=...` — БД отдаёт
за миллисекунды.

### P3. Нет индексов под канбан и поиск

Добавлена миграция `0019_perf_indexes`:

* `pg_trgm` + GIN-индексы на `lower(full_name)` / `lower(title)` — case-insensitive
  LIKE-поиск превращается из seq-scan в index-scan;
* `GIN(stack)` на обеих таблицах — фильтр по стек-тегам;
* `(status, kanban_order)` + частичный `(status, kanban_order) WHERE archived=false`
  — основной order_by канбана;
* `(candidate_id)` на `vacancy_candidates` для `_vacancy_ids_map`.

### P4. Все list-эндпоинты пагинированы, но dropped

Уже было `page`/`pageSize`, но фронт не использовал — см. B1/B2.

## Frontend-улучшения

* `CandidateKanbanCard` обёрнут в `React.memo` с прицельным сравнением
  (id/fullName/role/grade/rateMonth/daysInStatus/engagementType/stack). На
  200 карточек убирает ~40-60мс лишних рендеров при drag и WS-апдейтах.
* `KanbanCard` получил `onPrefetch` (pointerenter/focus); обе доски прокидывают
  `queryClient.prefetchQuery` для карточки. К моменту клика данные уже в кэше —
  открытие визуально мгновенное.

## Как замерить у себя (5 минут)

```bash
# 1. Postgres + Redis
docker compose -f infra/docker-compose.dev.yml up -d

# 2. Раскатать миграции (включая новую 0019_perf_indexes)
cd backend
make migrate

# 3. Засеять синтетику (1000 кандидатов / 50 вакансий / 500 связок)
PYTHONPATH=. python -m scripts.perf_seed

# 4. Поднять бэк
make dev   # uvicorn :8000

# 5. В другом окне — замер
PYTHONPATH=. python -m scripts.perf_bench \
  --email admin@lg.ru --password <ваш-admin-пароль>
```

Скрипт распечатает таблицу p50/p95/min/max по 8 сценариям. Чтобы сравнить
до/после: откатите ветку (или `git stash`), повторите шаги 4-5, сохраните
вывод, верните правки, повторите.

# КЭДО — план разработки по этапам

Архитектура и решения описаны в [`plan-hr-edo.md`](./plan-hr-edo.md). Здесь
порядок работ: этапы, задачи размером с PR, зависимости и критерии
готовности.

**Юридические тексты готовим позже.** Шаблоны документов (пакет согласия,
трудовой договор, приказы) в разработке — рыбы с пометкой
`ЧЕРНОВИК — ТЕКСТ НА СОГЛАСОВАНИИ У ЮРИСТА`. Движок от текстов не зависит:
шаблон — это HTML в `backend/app/modules/hr_edo/templates/`. Финальные
тексты подменяются без изменения кода.

Оценки — в днях одного фулстек-разработчика, с тестами. Это ориентир, не
обязательство.

## Этап 1 — ядро: согласие → своя УНЭП → подпись по SMS

**Результат этапа:** на staging кадровик заводит сотрудника, регистрирует его
согласие (скан), сотрудник по ссылке получает подпись и подписывает кодом из
SMS трудовой договор и приказ. У документа есть лист подписания и
неизменяемый протокол. Подпись директора на этом этапе загружается готовым
`.sig`.

Порядок PR — сверху вниз. Задачи 1.4 и 1.5 можно вести параллельно после
1.1.

### 1.0 Спайк `crypto-service` — 2–3 дня

Папка `spikes/crypto/`, по образцу `spikes/screening`.

- Java 17 + КриптоПро JCP в Docker: генерация ключевой пары ГОСТ 34.10-2012
  256, подпись хеша в отсоединённую CAdES-BES, проверка.
- Метка времени (CAdES-T) через публичную TSP — проверить доступность
  с staging-VM.
- Независимая проверка: `.sig` открывается в КриптоАРМ / `cryptcp -verify`.
- Выход: решение «JCP или CSP для Linux», замеры скорости подписи, заметка
  в `docs/`.

### 1.1 Фундамент модуля — 2 дня

- Модуль `backend/app/modules/hr_edo/` с README.
- `doc_types.py` — матрица типов документов и тест-законник
  `test_hr_doc_types_matrix.py`.
- Миграция `0036_hr_edo`:
  - таблицы `hr_employees`, `hr_signing_keys`, `hr_documents`,
    `hr_signatures`, `hr_sign_challenges`, `hr_doc_events`,
    `hr_access_tokens`;
  - триггер, запрещающий UPDATE и DELETE на `hr_doc_events`;
  - новые значения enum: `NotificationKind.hr_document`,
    `FileEntityType.hr_document`.
- `evidence.py`: запись события с хеш-цепочкой и `verify_chain()` + тесты.
- Права:
  - в `permissions/defaults.py` — 4 строки `hr_edo.*`;
  - синхронно в `frontend/src/lib/permissions-data.ts`;
  - тест backfill.
- Новые настройки в `core/config.py` и `.env.example`: `SMS_*`,
  `CRYPTO_SERVICE_URL`, `HR_EDO_*`.

### 1.2 Реестр сотрудников — 3 дня

- **Бэкенд:**
  - CRUD `/hr-edo/employees`;
  - `POST /hr-edo/employees/from-candidate/{id}` — только для `hired`,
    переносит ФИО, контакты и `employment_type`;
  - все проверки через `require_action`.
- **openapi.yaml** → `pnpm codegen`; MSW-handlers.
- **Фронт:**
  - сайдбар: группа «Кадры», пункты «Кадровые документы» и «Мои документы»;
    `ScreeningNavAction` → `NavAction`;
  - роут `_authed.hr-docs.tsx`, `HrDocsPage` с вкладками; вкладка
    «Сотрудники» — таблица и `FilterBar`;
  - `EmployeeSheet` (данные, статус КЭДО пошагово), форма создания и
    редактирования;
  - кнопка «Оформить сотрудника» в карточке кандидата в статусе `hired`.

### 1.3 Документы: шаблоны и заморозка — 4 дня

- **Шаблоны** (рыбы):
  - `edo_consent_package`;
  - `employment_contract`, `supplementary_agreement`;
  - `order_hire`, `vacation_request`, `order_vacation`;
  - `lna_acknowledgment`.

  Верстка и типографика — как у офферов: Golos Text, `normalizeText`,
  `@page`.
- **Бэкенд:**
  - `POST /hr-edo/documents/preview` отдаёт HTML;
  - `POST /hr-edo/documents` — черновик;
  - `/freeze`: рендер PDF через `pdf_service`, SHA-256 и Стрибог, загрузка
    в S3 (`hr-edo/`), событие `frozen`;
  - загрузка готового PDF для типов `upload_only`;
  - сквозная нумерация по типу и году;
  - `/cancel`.
- **Фронт:**
  - вкладка «Документы»: таблица, фильтры, статус-бейджи;
  - `CreateDocumentDialog`: тип и сотрудники через `SearchablePick`, поля,
    живой предпросмотр;
  - `DocumentSheet`: предпросмотр через pdfjs, таймлайн событий.

### 1.4 SMS и одноразовые коды — 2 дня

- `integrations/sms.py`:
  - интерфейс `send` / `status`, реализация под выбранного провайдера;
  - режим `log` только в `ENV=dev`, иначе падение при старте.
- `hr_edo/otp.py`:
  - челленджи с `purpose` (`portal_login` / `key_issue` / `sign`);
  - HMAC кода, TTL 5 минут, 5 попыток;
  - повторная отправка не чаще раза в 60 с;
  - лимиты в Redis: 5 в час и 15 в сутки на сотрудника, 30 в час на IP.
- Скраббер телефонов и кодов в Sentry.
- Celery: `hr_edo.poll_sms_status`.
- Тесты: весь набор сценариев OTP из плана, включая «кода нет в логах».

### 1.5 `crypto-service` — 4 дня

Зависит от 1.0.

- `services/crypto/`: Java-сервис на JCP.
  - Эндпоинты: `POST /keys`, `POST /sign`, `POST /verify`,
    `POST /keys/{id}/revoke`.
  - `/sign` принимает только валидный одноразовый `activation_token`
    (JWT на 60 с, отдельный секрет, привязка к `key_id` и `digest`).
  - Собственный append-only журнал операций.
  - Мастер-ключ хранилища — из Lockbox.
- `infra/docker-compose.dev.yml` и `prod.yml`: сервис во внутренней сети,
  без публикации порта. Volume для keystore и его бэкап.
- `integrations/crypto_service.py` в бэкенде; no-op-режим с пометкой
  «тестовая подпись» только в dev.
- `docs/runbook.md`: раздел «crypto-service» — запуск, бэкап, ротация,
  лицензия.

### 1.6 Согласие и выпуск подписи — 3 дня

- **Бэкенд:**
  - `POST /employees/{id}/invite`: формирует и замораживает пакет согласия,
    создаёт ссылку `hr_access_tokens`, отправляет письмо;
  - `POST /employees/{id}/consent`: загрузка скана или `.sig`, статус
    `consent_signed`, событие;
  - выпуск ключа: `key/otp` → `key/issue` → `crypto-service /keys` →
    `hr_signing_keys`, письмо с отпечатком ключа;
  - `keys/revoke` и смена телефона: отзыв ключа, сброс в `consent_signed`.
- **Фронт:**
  - `ConsentRegisterDialog`;
  - кнопки в `EmployeeSheet`;
  - `KeyIssueFlow` для портала и для «Моих документов».

### 1.7 Портал и подписание — 5 дней

- **Бэкенд, публичный роутер `hr_sign_public.py`:**
  - вход по токену + SMS, httpOnly-сессия на 30 минут;
  - список и файлы документов; события `viewed` и `viewed_to_end`;
  - челлендж подписи для пакета документов → confirm → `activation_token` →
    `crypto-service /sign` → `/verify` → `.sig` в S3 → `hr_signatures`;
  - отказ с причиной.
- **Бэкенд, закрытый API:**
  - `/send` — отправка документа сотруднику;
  - `GET /hr-edo/my/documents` — те же операции для пользователя CRM без
    SMS-входа;
  - `POST /documents/{id}/employer-signature` — пока загрузка готового
    `.sig` директора с проверкой через `crypto-service`.
- **Лист подписания:** HTML-страница → PDF, склейка с исходником →
  `stamped_file_id`. Исходный PDF не меняется.
- **Фронт:**
  - публичный `routes/sign.$token.tsx`, `SignPortalPage` (mobile-first);
  - `SigningFlow`: просмотр, прокрутка до конца, чекбокс, подпись;
  - `OtpInput` (`one-time-code`, WebOTP), экран успеха;
  - `MyDocsPage` с бейджем в сайдбаре.

### 1.8 Уведомления, напоминания и доводка — 2 дня

- `notify(kind=hr_document)` сотруднику-пользователю CRM и кадровику
  (подписан, отказ); Telegram — через outbox.
- Celery beat: `hr_edo.remind_unsigned` (10:00 МСК), `expire_documents`,
  `verify_event_chain`.
- Протокол событий в `DocumentSheet`, вкладка «Журнал».
- Прогон:
  - `ruff`, `mypy`, `pytest`;
  - `pnpm typecheck`, `pnpm lint`, `pnpm codegen:check`;
  - ручная проверка на iOS Safari и Android Chrome, тёмная тема.

**Итого по Этапу 1: ~27–30 дней.**

**Критерии готовности Этапа 1** (сквозной сценарий на staging):

1. Сотрудник заведён из кандидата.
2. Пакет согласия зарегистрирован сканом.
3. По ссылке сотрудник получил подпись по SMS и видит отпечаток ключа.
4. Трудовой договор и приказ о приёме подписаны одним кодом.
5. `.sig` проходит независимую проверку в КриптоАРМ.
6. `stamped.pdf` содержит лист подписания.
7. Протокол целостный, попытка правки `hr_doc_events` отклоняется БД.
8. SMS с кодом нет ни в логах, ни в Sentry.

## Этап 2 — подпись директора в системе и доказательная база

**Результат этапа:** директор подписывает в CRM своим токеном. По любому
документу можно выгрузить пакет для ГИТ, ФНС или суда. Подписи проверяются
через десятилетия.

### 2.1 УКЭП директора в браузере — 4 дня

- `EmployerSignDialog`: cadesplugin, выбор сертификата, подпись
  CAdES-X Long Type 1 (TSP и OCSP).
- Очередь «Ждут моей подписи» на странице «Кадровые документы».
- Порядок `employer_first` / `employee_first` из матрицы.
- Массовая подпись нескольких документов.

### 2.2 МЧД — 2 дня

- Загрузка машиночитаемой доверенности для подписанта-не-директора.
- Проверка полномочий на тип документа, поле `poa_file_id`.

### 2.3 Пакет доказательств и проверка — 4 дня

- `GET /documents/{id}/evidence.zip`: состав по приказу 578н,
  `wredc_data.xml` по XSD Минтруда, валидация в тесте.
- Публичная страница `/verify/{signatureId}` и QR на листе подписания.
- Массовая выгрузка пакетов за период (Celery → zip в S3 → ссылка).

### 2.4 Архивное хранение — 3 дня

- PDF/A через Ghostscript, спайк для PDF/A-1A.
- Object Lock с retention по `retention_years` для исходников, `.sig` и
  снимков журнала `crypto-service`.
- Ежедневный снимок журнала `crypto-service` в S3.

### 2.5 Пакетные рассылки — 2 дня

- `POST /hr-edo/batches`, например «ознакомить всех с ЛНА».
- Прогресс рассылки, напоминания только неподписавшим.

**Итого по Этапу 2: ~15 дней.**

**Критерии готовности:**

- трудовой договор подписан директором в CRM и сотрудником по SMS;
- `evidence.zip` проходит проверку XSD;
- обе подписи проверяются сторонним ПО;
- `/verify` по QR показывает корректный статус.

## Этап 3 — ГПХ, Госключ, сервисы сотрудника

### 3.1 ГПХ-контур для ИП и СМЗ — 4 дня

- Типы `gph_edo_agreement`, `gph_contract`, `gph_act`.
- Та же УНЭП ЛГ на основе рамочного соглашения.
- Проверка бизнес-правила: никаких трудовых формулировок.
- Для СМЗ — поле и файл чека «Мой налог» у акта.

### 3.2 Госключ — 3–5 дней

По итогам спайка.

- Проверка `.sig` Госключа для пакета согласия прямо в портале.
- Госключ как альтернативная подпись документов.

### 3.3 Заявления сотрудника — 3 дня

- Шаблоны заявлений: отпуск, копии документов по ст. 62.
- Сотрудник подаёт заявление из портала; для запроса копий — SLA 3 рабочих
  дня с таймером у кадровика.

### 3.4 Архивные операции — 2 дня

- `hr_edo.archive_retimestamp` — ежегодно.
- Отчёт о сроках хранения, акты уничтожения.

**Итого по Этапу 3: ~12–14 дней.**
